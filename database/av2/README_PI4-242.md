# PI4-242 — Implementar o modelo físico do FolcStore

## Objetivo

Implementar as **13 tabelas do modelo lógico aprovado**, em SQL PostgreSQL, com IDs inteiros, campos monetários `NUMERIC(12,2)` e restrições nomeadas `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`, `DEFAULT` e `CHECK`.

> **Importante:** esta pasta é a implementação **SQL da AV2 de Banco de Dados**, não uma substituição imediata do backend. O `prisma/postgresql/schema.prisma` já existente usa UUIDs, perfis e preços em centavos, por isso **ainda não é compatível com este novo modelo**. Não execute migrações Prisma antigas por cima deste banco. A adaptação de services/repositories e schema Prisma será uma etapa separada.

## Arquivos

- `ddl.sql`: criação transacional das 13 tabelas e seus índices, sem DROP e com proteção contra banco não vazio.
- `verificar_modelo.sql`: confere presença das 13 tabelas e mostra número de restrições.
- `testes_integridade.sql`: demonstra duas recusas esperadas pelo banco, sem gravar dados permanentes.

A história seguinte (**PI4-243**) produzirá `seed_dml.sql` com pelo menos 3 registros por tabela e ao menos 10 produtos para atender também à disciplina de IA.

## Como executar no seu computador (PowerShell)

Coloque esta pasta em `database/av2/` **na raiz do seu fork do backend**. Os comandos seguintes partem da pasta raiz `folcstore-backend`, usando o PostgreSQL que já foi criado na PI4-241.

1. Confira que o contêiner está saudável:

```powershell
docker compose --env-file .env.postgres -f compose.postgres.yaml ps
```

2. Copie o script para dentro do contêiner e execute. **Faça isto apenas no banco local e vazio**, sem dados que precisem ser preservados:

```powershell
docker compose --env-file .env.postgres -f compose.postgres.yaml cp database/av2/ddl.sql postgres:/tmp/ddl.sql
docker compose --env-file .env.postgres -f compose.postgres.yaml exec -T postgres psql -U folcstore -d folcstore -v ON_ERROR_STOP=1 -f /tmp/ddl.sql
```

Deve mostrar 13 linhas `CREATE TABLE`, linhas `CREATE INDEX` e terminar com `COMMIT`. Como o script contém `BEGIN`/`COMMIT`, qualquer erro antes do COMMIT faz a transação falhar. **Não execute novamente em banco já criado**: o bloqueio de segurança impede reutilização indevida.

3. Execute a verificação:

```powershell
docker compose --env-file .env.postgres -f compose.postgres.yaml cp database/av2/verificar_modelo.sql postgres:/tmp/verificar_modelo.sql
docker compose --env-file .env.postgres -f compose.postgres.yaml exec -T postgres psql -U folcstore -d folcstore -v ON_ERROR_STOP=1 -f /tmp/verificar_modelo.sql
```

4. Execute os testes de erro controlado:

```powershell
docker compose --env-file .env.postgres -f compose.postgres.yaml cp database/av2/testes_integridade.sql postgres:/tmp/testes_integridade.sql
docker compose --env-file .env.postgres -f compose.postgres.yaml exec -T postgres psql -U folcstore -d folcstore -v ON_ERROR_STOP=1 -f /tmp/testes_integridade.sql
```

Resultado esperado: mensagens `NOTICE` iniciadas por `OK teste 1` e `OK teste 2`. São falhas intencionais capturadas dentro dos testes para que eles sejam reproduzíveis.

> Caso suas variáveis `POSTGRES_USER` ou `POSTGRES_DB` no `.env.postgres` sejam diferentes de `folcstore`, substitua `-U` e `-d` nos comandos. A senha local fica no `.env.postgres` ignorado pelo Git, nunca nos scripts SQL.

## Principais decisões físicas da PI4-240

| Tema | Implementação |
|---|---|
| Perfis | `usuarios` e especializações `compradores`, `artesaos`, `administradores` (PK/FK compartilhada) |
| Identificadores | `INTEGER GENERATED BY DEFAULT AS IDENTITY` para IDs próprios; FKs `INTEGER` |
| Categoria | `produtos.categoria VARCHAR(100)` (sem tabela extra) |
| Dinheiro | `NUMERIC(12,2)` em produtos, carrinhos e pedidos |
| Endereços | `pedidos.id_endereco` referencia `enderecos.id`, sem exigir que seja residência do comprador |
| Produto | `RASCUNHO`, `ATIVO`, `PAUSADO`, `INATIVO` |
| Pedido | `PENDENTE`, `CONFIRMADO`, `EM_PREPARACAO`, `ENVIADO`, `ENTREGUE`, `CANCELADO` |
| Peça única | Produto `UNICO` não pode ter estoque acima de 1 |
| Integridade histórica | `RESTRICT` em relacionamentos de pedidos, avaliações e postagens; `CASCADE` em imagens e itens de carrinho |

## Regras fora do alcance de um CHECK simples

A soma de `itens_pedido.subtotal` igual a `pedidos.valor_total`, a garantia de que a postagem pertence ao artesão dos itens, a verificação de compra antes de avaliação e as transições permitidas entre status exigem validação transacional no serviço ou gatilhos adicionais. **Não são garantidas pelo DDL aqui entregue.**

O modelo lógico tem `imagens_produto.id` como PK e foi seguido neste script; no diagrama Chen, a identificação da entidade fraca pode requerer esclarecimento com o professor. Os três subtipos de `usuarios` não são obrigatoriamente exclusivos no SQL, porque o diagrama não formalizou essa regra.

## Segurança e versionamento

Execute somente no banco acadêmico local configurado na PI4-241. Não execute em banco de produção ou com dados reais. Não commite `.env.postgres`, volumes de banco ou senhas. Para manter a entrega no fork:

```powershell
git add database/av2/ddl.sql database/av2/verificar_modelo.sql database/av2/testes_integridade.sql database/av2/README_PI4-242.md
git commit -m "feat(db): implementar modelo fisico PostgreSQL PI4-242"
```
